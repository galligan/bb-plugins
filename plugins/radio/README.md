# Radio

Short transmissions. Durable coordination.

Radio is a BB plugin being built for communication between people, BB threads, persistent bots, and external agents. The intended product uses transmissions for the essential update or request and dispatches for supporting detail. Participants will be able to listen to channels, reply, acknowledge, accept responsibility, and broadcast to a defined audience without treating every message as permission to start work.

**Status: internal communication services.** `bb-plugin-radio` has a backend package and tests against BB 0.49.0 / public SDK 0.6.132. Loading the backend initializes plugin-owned SQLite storage through append-only migrations. Its internal domain API provides a stable station and human identity, actors, BB threads, external sessions, project/main-channel/subchannel records, handles/aliases, address parsing/resolution and immutable transmissions/replies with exact replay, versioned Markdown dispatches, and explicit receipt/ack/standby/squelch facts, commitments, exclusive claims, exact-channel subscriptions/broadcast snapshots and an attention digest. There are no communication commands, RPC/native tools, HTTP routes, UI or marketplace entry yet. CLI examples and adapter API shapes remain proposed until their surface layers land. The design was developed with Matt and researched on 2026-11-10; its unresolved decisions remain open.

Readable project/channel names are normalized before allocation or rename: `Pay__Ments` becomes `pay-ments`, and `cut--over` becomes `cut-over`. Results include the requested and canonical spelling and whether it was corrected. Names contain at most 64 lowercase ASCII letters/digits with single hyphens between segments; raw input is bounded to 256 characters. Empty or oversized results are rejected without truncation, and collisions never reassign an existing identity. Renames preserve canonical IDs. Actor display names and opaque IDs are separate from readable addressing names.

External registration receives trusted principal context separately from strict self-reported metadata. Client session IDs are unique within that principal; they never replace canonical Radio IDs or grant ownership of another actor. Session names, providers and models stay on their session records; the durable principal actor does not inherit or track one session's report. BB thread registration preserves its existing ID and requires an explicit owner actor, without inferring ownership from parentage. These are internal domain contracts; authentication and public adapters are later layers.

Handle assignment and rename require adapter-authenticated owner or human context. Ordinary renames retain aliases. Human reclaim transactionally assigns a primary name, allocates a collision-free fallback for a displaced primary holder and records the reassignment. Reclaiming an alias leaves its prior holder's current primary intact. Name collisions, aliases and self-reported metadata cannot grant authority to change another identity.

The body parser preserves original text/offsets and returns canonical tokens with correction information. Literal quotes, inline/fenced code, blockquotes and escapes do not expand addresses; malformed syntax fails before resolution. Resolution receives an explicit authorized project scope, refuses cross-project fallback and returns qualified choices on ambiguity. `ch:` references and `@ch:` audiences resolve to the same channel ID with distinct token kinds. The transmission service freezes direct recipients and explicit channel audiences. It does not deliver messages or start turns. See [identity](docs/identity.md) for the literal-region and authorization contracts.

The internal `transmissions.send(context, request)` operation atomically stores immutable content, canonical refs/tags, direct recipients and the author/principal-scoped replay binding. Context contains authenticated author/session ownership and project access. An identical retry returns the original ID and audience even after handle reassignment; a changed request with the same key conflicts. Reads and cursor-based channel scans check authorized project scope and never manufacture receipt evidence. Replies stay in their accessible parent channel and inherit no audience; mention or supply recipients explicitly.

Bodies contain 1–400 Unicode code points, counting all inline tokens and Markdown; the raw input cap is 2000 UTF-16 code units. Nothing is truncated or rewritten. Requests allow 16 structured HTTP(S) URL/canonical transmission/participant/channel refs and 100 distinct direct recipients (at most 1000 raw recipient-ID entries); scans return at most 50 records. External refs are stored without fetching or claiming access. Explicit channel broadcasts atomically select unmuted listeners of that exact channel and return frozen per-channel eligible counts, including zero. Overlapping IDs deduplicate, while two sessions of one actor remain distinct; overflow rejects the whole send rather than accepting a partial audience. See [protocol](docs/protocol.md) for the implemented contract and remaining planned semantics.

Owned dispatches live in the plugin database with a stable ID and immutable full revisions. The original author or explicit station human can revise them; each revision records editor/session provenance and requires the expected current revision, so stale edits conflict. Reads check authorized project scope and accept a pinned revision or latest. Titles use 1–120 UTF-16 units and Markdown is capped at 65536 UTF-8 bytes. Lists return at most 50 titles/revision numbers without Markdown. Their cursors paginate stable document creation order; refresh the listing or read a document to observe edits, since this is not an edit-change feed. Creation/revision writes replay exactly after response loss; failed writes roll back document, revision, latest pointer and replay binding. Transmission dispatch refs resolve latest to a pinned revision at acceptance, and retries retain that revision. HTTP(S) URL refs remain links only, without fetching or granting access. Rendering and public adapters are later layers.

The internal `responses.record` operation records an authenticated participant's explicit `received`, `ack`, `standby` or `squelch` fact. A receipt requires recipient confirmation of actual content and identifies its concrete acting session (or the human endpoint); duplicate confirmations do not inflate counts. Actor and session targets stay independent. Acceptance, ordinary reads, count summaries and ack never create receipt evidence. `standby` means waiting without a work commitment; `squelch` records dismissal without closing obligations. Facts record acting-session provenance, replay by scoped key and survive reopen. Event pages are bounded to 50; summaries cover exactly the frozen recipient IDs. Commitments/claims are available through the separate internal service below. None of these operations wakes a session.

`commitments.act` implements `wilco`, `done` with a concise result, `abandon` with a reason, and original-author `reopen` of an abandoned exclusive request. Discussion permits independent commitments by multiple participants; each target gets one commitment per tx. An exclusive request atomically has one winner. With explicit recipients, only those exact targets can claim; an unassigned request can be claimed by an authenticated participant with channel access. Abandonment retains the closed claim until the original request author explicitly reopens it, starting a new claim generation without changing old commitments or the frozen audience. Completed requests stay closed.

Actor commitments survive a new owned acting session, retaining opening and event provenance. A specifically addressed session requires that exact session to act; no implicit transfer, delegation, waiver or expiry exists. Standby/squelch do not close commitments; wilco/done never imply ack/receipt. Open commitment lists paginate by owner and accessible project without recent-message filters. Action retries return the original operation snapshot even after later closure/reopen; explicit reads return current state. New transmissions can opt into `requestMode: "exclusive"`, `requireAck` and `expectReply`; defaults preserve shipped request replay encoding.

`subscriptions.set` implements listen/mute/unlisten for the authenticated invoking session by default, or its explicitly selected actor. Listening validates project access; owners can always mute/remove an existing binding after access loss. Actor/session ownership is shared with response and commitment checks. Lists are project-scoped and bounded to 50. Subscriptions are explicit in this internal layer; automatic project-main listening remains a proposed registration default for later adapters. Main and subchannels do not include each other's listeners. Mention multiple `@ch:` channels to combine them. A direct `ch:` reference never expands an audience. Mute/unlisten affect future selection and passive discovery, never old recipient snapshots, direct mentions, required responses or open commitments. Credential adapters must invalidate subscription eligibility when authorization is revoked; no credentials or execution permissions are created here.

`attention.check` returns three independently paginated groups: recent discovery, required responses, and open commitments. Discovery follows the invoking actor/exact session's direct targets, unmuted subscriptions and replies to its own posts, suppressing unrelated sibling-session inbox activity. Required responses and open work remain visible across the owner's sessions, labeled by exact canonical target, without recent-message cutoffs; mute/squelch never waive them. Counts are explicitly `pageCounts`, not global totals; each group reports `hasMore`. Every read is project-scoped and never records receipt or starts a turn.

Reply expectation coverage is separate from acknowledgment. A linked reply selects one owned original recipient through `replyForId`; a sole eligible target is selected automatically, but mixed actor/session eligibility requires an explicit canonical choice. Only that recipient's reply requirement is satisfied, and the other stays open. A reply adds no inherited audience or automatic ack/receipt. The original author can discover a response without adding a synthetic recipient. Historical replies without an explicit coverage record do not retroactively claim coverage.

## Development

Use the repository's Bun 1.3.14 and Node 24.x runtimes. Install dependencies at the repository root with `bun install --frozen-lockfile --ignore-scripts`. From this directory, run `bun run check`, `bun run test` and `bun run build`; run `bun run verify` at the repository root before pushing.

Tests use the public SDK fake host and real temporary SQLite databases. They cover first load, repeated initialization, database reopen, plugin reload/disposal, independent station identity, failed migration rollback, changed migration history, metadata provenance, principal-scoped external sessions and project/channel renames. This establishes the storage contract in the harness, not live BB installation or delivery behavior. BB owns the database handle and closes it on reload/disposal; Radio does not close the shared handle itself.

The current schema contains station, participant, project, channel, handle, reassignment, transmission, frozen recipient, dispatch and revision records. Receipt/response facts are stored separately; commitment/claim history is durable, and subscription state is durable; the attention digest reads durable state without recording receipt. Zod validates boundary requests and metadata. SQLite and harness peers remain development dependencies; the host supplies the runtime database.

## Example

```sh
bb radio listen ch:payments/cutover
bb radio tx --ch payments/cutover \
  "@ch:payments/cutover Cutover moved to Thursday. Confirm readiness. #release" \
  --ref dispatch:D-42
bb radio check
bb radio ack TX-17
bb radio wilco TX-17
bb radio reply TX-17 "Migration verified against staging." --done --ref pr:142
```

A broadcast creates one transmission with individual recipient records. Reading a count is not receiving the transmission. Receiving it is not acknowledging it. Acknowledging it is not accepting work. Accepting work is not completing it.

The next adapter foundation includes `LocalContexts`: verified BB thread/project routing, atomic actor/session bootstrap, preservation of explicit mappings and separate operator-credential validation for human authority. Missing context never selects `@user`; native attribution cannot inherit a human/external actor mapping. These helpers do not yet register public commands/tools/RPC or provision credentials. Matt chose an initial trusted-environment outside-agent test without credentials; the future HTTP adapter will keep that shared test principal separate from operator authority. See [adapter authority](docs/decisions.md#released-adapter-authority-decisions).

Verified local project bootstrap keeps an existing Radio mapping. For a new project whose BB display name is invalid, reserved, too long or already allocated after normalization, it uses a bounded `project-` qualifier derived from the immutable BB project ID. It never truncates the proposed name, displaces another project or silently renames an existing mapping. The resulting canonical qualifier is returned by project registry reads and remains explicitly renameable. BB thread IDs are opaque and retain hyphenated suffixes without applying readable-name normalization.

`RadioOperations` prepares one strict operation contract for the upcoming CLI, RPC, native tools and trusted-test HTTP adapters. It includes tx/reply/read/scan/check, explicit protocol/commitment actions, subscriptions, dispatches, project/channel names and handle/alias operations. Credentials and author claims are absent from operation inputs; adapters supply verified context separately. Scan projects bounded summaries, with full refs/tokens available through a single read. Own-tool hints are one-item samples plus `hasMore`, never total counts or receipt evidence. Public adapter registration remains the next layer.

Transmission requests now accept exactly one canonical `channelId` or readable `ch` path (`project` or `project/subchannel`). The source path is bound to its idempotency key before resolution: retries after rename/name reuse return the original canonical channel and audience, with current access still checked. Legacy canonical-ID request encoding remains replayable.
