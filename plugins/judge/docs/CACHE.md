# Whole-request cache and run retention

Ordinary explicit asks and saved-set steps reuse complete validated provider responses for up to 60 seconds. This is a whole-request cache: its SHA-256 key includes the versioned transport contract, actual resolved model fingerprint (including endpoint/model configuration and opaque connection revision), canonical complete question-map hash and canonical state hash. Object key order does not change identity; a changed question, rubric, batch, state, model policy/limit/selector or connection cannot reuse the old answer. Per-question hashes are diagnostics only, never separate cache entries. There is no cross-batch equivalence assumption.

Privacy resolution and fresh BB connection reads happen before lookup, and model/current-generation checks still happen before returning a hit. A sensitive call can reuse only the actual allowed private configuration. Requested model IDs and fallback reasons come from the current selection, rather than the cached caller. Changing a model/default/set/project/connection clears inference cache and calibration conservatively; plugin reload also retires opaque identities. No secret value is included in a hash. Cached answers do not permit bypassing revoked private policy, missing credentials, cancellation or the caller's whole deadline.

Only fully validated successful batches enter the SQLite cache, after the final asynchronous model/settings check and the whole inference scope accept success. A final synchronous scope/generation guard inside the insertion transaction rolls back cancellation or expiry during storage. Rows contain the hashed descriptor, per-question hashes, returned provider label and typed answers. They contain no input state, question instructions or credentials. Score legends remain part of their validated answers and can repeat authored rubric data; answers themselves can be sensitive, as with bounded run history. Corrupt stored entries fail closed as operational storage errors, without silently making a paid retry. Cache insertion/pruning failures are operational failures and cannot claim a successfully recorded ask. There are no retries, background refreshes or in-flight request coalescing.

A hit still creates a new run/step record, with `cacheHit:true`, the current requested/resolved identity and source provenance, and freshly evaluated outcomes. `latencyMs` measures the current lookup operation and `inputTokens:0` means no tokens were sent for that hit; the original provider label is retained. A cache entry does not store outcomes, gates, acceptance, thread/project attribution or a previous run ID. Ad hoc asks remain uncalibrated; saved-set calibration still checks the current accepted set hash and all actual fingerprints.

**Case evaluations and connectivity probes always bypass both cache reads and writes.** Repeated `judge test` and `models check --probe` measure fresh explicit provider requests and can incur charges; they cannot report an old cached response as new provider evidence. The bypass is internal to these workflows, not a public privacy override or extra CLI/RPC option.

The cache keeps at most 1,000 entries and uses a 60-second TTL, expired at the exact boundary. It prunes expired/future-clock rows and oldest excess entries transactionally during writes. Reads do not refresh age or serve future timestamps after clock rollback. A validated response that cannot fit its diagnostic envelope within 1 MiB is returned uncached. Request/response and whole-execution bounds remain in force around hashing, validation and storage. Retention is opportunistic; expired rows can remain on disk until another write, but are never served.

Run history retains its existing 30-day/10,000-run limits. Successful run writes prune by start time, then newest timestamp/run-ID order, in the same transaction as the run and ordered steps. The exact 30-day age boundary remains eligible until the next millisecond; dependent steps cascade when their run is deleted. A failed insertion or prune rolls the entire transaction back, preserving previous runs and steps. Evaluation report retention is separate, as described in [evaluation](EVALUATION.md).

Offline tests cover whole-map/canonical identity, state/question/config/endpoint separation, typed answer/rubric round trips, private fallback attribution and revocation, rotation/removal/reload, exact TTL/clock rollback/caps, no outage/abort caching, in-flight invalidation, fresh evaluation/probes, per-run outcomes/provenance, corrupt read refusal and transaction rollback. Clock-controlled run tests cover the age boundary, all dependent rows, deterministic 10,000-run retention and rollback. Live provider quality, triggers, UI and remote-host workflows retain their separate gates.
