# Judge settings and verdict display

The Judge frontend vendors BB 0.49 registry button, input, textarea, checkbox and radio-group recipes with their support files. The fixed three connection choices and two event choices use labeled radio groups with keyboard navigation, without a popup. It adds a **Models and verdicts** section to Settings → Installed plugins → Judge [Experimental]. BB continues to own the flat connection fields and all secret entry. The frontend never requests or receives a key. Credential saving, readiness, model/default/project/binding saves, report loading and explicit calibration acceptance make no inference request. No model/default is selected automatically.

Model controls create or replace a saved ID, choose Jev / TypeSafe, Workers AI or custom System One, set the provider selector and timeout, and explicitly permit private data. Editing a model preserves its other saved limits. Defaults select an existing ID; empty clears it, and a private fallback must permit private data. Distinct stale-calibration, private-fallback, missing-set/model/binding and unknown-outcome refusals preserve only fixed allowlisted reason messages across RPC; arbitrary validation/upstream exceptions stay sanitized. Project/report Load buttons explicitly retry unchanged IDs after failed reads. Models, defaults, bindings and connection readiness retain visible read-only refresh controls after a first-load failure. Readiness is sanitized and performs no provider probe. A configured connection is not evidence of live support. Workers AI selectors remain `clef` and `clef-flash`; custom URLs and all credentials use BB's native fields above.

Project controls load an explicit project ID and toggle Judge applicability. The effective policy still intersects the saved-set and event-binding project filters. A project edit disables bindings and retires calibration, even when allowing the project. Saved-set authorship/import remains available through the implemented CLI; the UI does not invent a second definition format.

Calibration controls load an existing case report by ID, show primary/comparison mismatch counts, actual resolved identities/fingerprints, and per-case expected/observed final outcomes without inputs or raw answers. Current acceptance is separately checked. After reviewing the primary evidence, an explicit acknowledgement enables the acceptance button for a complete, non-stale report. The server rechecks current suite/hash/model policy before acceptance. A complete report with mismatches may be deliberately accepted; this is an acceptance decision, not a correctness certificate. Acceptance never enables a binding. Use `bb judge test <set-id> --json` for explicit paid case evaluation; loading a report does not run it again.

Binding controls list 20 records per page, create/replace disabled bindings, and separately enable, disable or remove them. Enable requires a visible paid-request acknowledgement followed by an explicit button click. This UI friction is not an agent-proof permission boundary. Saves omit enabled state, allow only idle/failed events, and reuse the server's set/outcome/project validation. Empty badge maps are record-only. Model, set and connection changes retain the existing invalidation behavior; bindings never override private-data policy.

## Thread Info and optional sidebar badges

The **Judge** Info row is always registered and useful with sidebar metadata off. It displays current configured labels, latest run state (current, recorded but not current, uncalibrated, incomplete or unavailable), unavailable code, time, saved model ID, configured selector and returned provider label when present. No source state or raw answers are included in the display DTO. An empty thread says it has no recorded runs; read failures are visible with a Refresh control. Historical model identity remains labeled as the latest recorded run, never current calibration or authorization.

The separate **Show Judge sidebar badges** setting defaults off. Sidebar labels also require BB's `threadRowMetadata` experiment and Organize → Rows → Metadata, both controlled by BB. Enabling this display setting neither changes model policy nor establishes calibration or triggers inference. The row hook reads visible IDs in sequential keyed batches of at most 200 and never makes per-row SDK reads. Labels are capped at 20 per display row with an explicit remaining-count indicator; the underlying metadata remains capped at 20 summaries/32 KiB.

The server's `ui.badges` and `ui.thread` projections reuse authoritative verdict reads. Both server and client validate bounded display shapes. Invalid/forged raw metadata is hidden; metadata publication failures are shown as sanitized codes. Client reads clear their previous display immediately on `changed` signals and reject obsolete asynchronous results. Reconnects reread durable server state. Invalidation messages contain no run data: configuration flags and affected thread IDs are coalesced over 50 ms with a 200-ID cap. Events for other threads do not invalidate a mounted view or refresh settings. Model/default/set/project/binding/calibration edits, new runs, publication completion/cleanup, and thread lifecycle observations signal refresh. Optional sidebar state does not control the Info row.

Display metadata is not authorization or independently verified fact. Best-effort SDK metadata cleanup and non-atomic source observations retain the limitations in [TRIGGERS.md](TRIGGERS.md). Browser tests use BB's public frontend harness and JSDOM, including refresh, delayed responses, invalid metadata, default-off reads and batching. Actual host layout, theme, navigation and remote/sleeping host behavior require the recorded live checks; deterministic harness tests do not establish those properties.

## Local browser observations (2026-11-10)

Judge alone was installed/reloaded on BB 0.49.0 with public SDK 0.6.132. The local authenticated BB page rendered the settings controls with the host dark theme, labels and native keyboard focus. Selecting the existing `jev` model returned configured readiness without a probe. An invalid model ID produced the actionable field/JSON/limit hint; saving the original `jev-1.13.0`, public-only model succeeded and a fresh CLI read matched the original limits and null defaults. The optional sidebar display setting persisted on, then was restored off. No binding was enabled and the latest stored live run remained the original BBP-12 smoke.

The owner thread's Info row rendered with sidebar badges off: no current badges, latest run uncalibrated/ad hoc, and configured/returned `jev-1.13.0` identity. Missing report and empty-binding states were observed, with no acceptance button for the missing report. A late-read race, bad metadata, calibrated labels, acknowledgement/acceptance, and batches exceeding 200 IDs were exercised in the public frontend harness with synthetic fixtures. Screenshots and sanitized readiness/model/reload records are task artifacts, not distributed plugin content.

These observations establish the local UI paths above. A positive calibrated **live event → metadata → sidebar** scenario, actual event delivery/history retention, a signed-in remote browser and sleeping/remote-host cases remain BBP-23 gates. The remote page presented an account sign-in requirement in the automation browser; no account credentials were collected. No new provider call or private-data permission was used for these UI checks.

A subsequent local browser pass verified the BB registry radio controls, keyboard ArrowDown selection, the missing-set recovery hint and private-fallback refusal hint. Both refused writes left Jev public-only, defaults null and bindings empty; the browser session was closed. The final retry controls are additionally covered by isolated first-load failure/recovery tests.
