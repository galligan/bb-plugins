# Bots

Use `bb bot status` for supported features and `bb bot list` / `show <bot-id>` for identity, home, main and setup errors. Pull `bb bot brief <bot-id> --json` during ordinary turns when current state matters. It includes the calling worker's current contract, current revisions, future execution defaults and recorded task source and up to ten commitments with point-in-time status availability. Follow the continuation cursor when more obligations matter; memory remains unavailable. Volatile state is not guaranteed-fresh injected guidance. If another plugin owns the alias, use `bb plugin run bbots ...`.

`create --machine <host-id>` creates Bob; `--name` selects another name. It creates a persistent home outside repositories and starts one short setup acknowledgement. Retain an explicit `--request-id <uuid>` before scripted submission and reuse it only with identical options after uncertain delivery. `--association-mode none|all|selected` is responsibility scope; repeat `--project <id>` for selected projects. It does not move the main home or grant new permissions.

Use `resume <bot-id>` after restoring an offline machine or the recorded home. Resume reconciles existing progress without respawning an uncertain main or resending its prompt. A missing established home must be restored; never silently recreate an empty collaborator. Inspect native requests/queues when setup reports uncertain delivery rather than issuing another creation blindly. Native Stop applies per thread; inspect and explicitly cancel held queue entries when work must be discarded. Do not treat idle as permission to resume a canceled assignment. Bots cannot control another plugin's compaction/retry or the native Send now override.

Use `rename <bot-id> --name <name> --revision <current>` for an explicit revision-checked rename. Identity/home remain stable; existing pin preference is preserved. Use `soul show <bot-id>` to inspect revisioned SOUL.md and the `bbots-soul` skill for deliberate changes. It is not a live home file. Current revision and last supplied revision are separate; applied revision remains unknown without a provider receipt. Do not claim an already running session has refreshed instructions.

Use `models show <bot-id>` for future conversation defaults. `models update` saves a complete revision-checked JSON document with `main`, `worker` and `fallback` choices. A null worker inherits main; an explicit worker object defines independent native choices, with omitted values inheriting BB policy. A fallback cannot set permissions and automatic fallback remains disabled. Saving starts no turn and does not mutate an existing main. Use BB's native controls for that conversation's execution choices; provider/model/reasoning availability is validated by BB when a new conversation is created. Main creation also accepts `--provider`, `--model`, `--reasoning` and `--permissions`; omission preserves BB defaults.

## Owned work and communication

When the user authorizes a distinct assignment, use `bb bot work '<assignment>' --title '<short task>' --project <project-id> --environment <ready-environment-id> --author <truthful-identity> --reason '<instruction>'`. An owned caller supplies its bot automatically; an unowned caller must select `--bot <bot-id>`. Retain `--request-id <uuid>` before scripted submission. This starts the assignment in one normal native thread; it is not a dormant draft.

Parentage and reporting are separate. `--parent <thread-id>` is optional and must belong to the working project. Native parent notifications default off. `--parent-notifications auto` can duplicate explicit reports. Set `--report-thread <ordinary-thread-id>` or `--report-conversation <logical-id>` for a non-main destination. Omission records this bot's main as the initial target. Use `--report-when`, `--stop-when`, `--context` and repeated `--source` for the selected agreement; evaluate its triggers yourself. The plugin does not watch task completion.

Use `work list <bot-id>` to find recorded workers and request IDs, and `work show <conversation-id>` to inspect uncertain setup. Reusing a request never automatically respawns an attempted worker. Inspect native thread history and queue before deciding on a new action after an uncertain receipt.

Pull `contract show <conversation-id> --json` before reporting or continuing changed work. For a deliberate reassignment, `contract update <conversation-id> --revision <current> --agreement '<complete-json>' --author <identity> --reason '<instruction>'` appends a revision. Saving does not start a turn, reparent a thread or resume a stopped assignment.

Use `report '<message>'` from the owned worker for its contract destination. Use `msg '<message>'` for the current main; an unowned caller must select `--bot`. Use `reply '<message>' --seq <native-message-sequence>` for the native agent sender of that incoming message. Do not infer a reply destination from prose or substitute the main when a contract is missing. A title or writable metadata does not establish ownership.

These are explicit new communications. Native queue-if-active delivery can start a recipient turn when idle, including after Stop. A report does not authorize resuming a previously canceled assignment. Treat it as a new communication under current instructions. Return native acceptance/queue evidence; do not claim it proves reading, completion or a response. If delivery is uncertain, inspect native history and queue; do not blindly resend.

## Task source

Use `tasks show <bot-id>` to read task authority before choosing or changing work. `tasks select` and `tasks create` require an explicit source instruction, expected revision, author and reason. A configured tracker remains authoritative during an outage. The outage does not authorize a replacement or Markdown fallback; change an established authority only through the explicit assisted-migration procedure below. If creation is uncertain, inspect the recorded intent and native Tasks board before explicit `tasks recover` with its confirmed stable ID. Prefix matching does not prove original identity after deletion/reuse; confirm the intended board independently.

When Tasks is absent at the initial task-source choice, use `tasks markdown-init` with the expected source revision, author and reason. Inventory must confirm absence; disabled Tasks and RPC errors are not absence. Use `tasks markdown-resume` only to reconcile the same interrupted initialization. Do not overwrite an occupied file or choose another home.

In Markdown mode, use `tasks read` and `tasks write --hash <current-hash> --markdown '<complete-file>'`. These operations route to the original home host, including from remote workers. Preserve the complete file; arbitrary Markdown has no inferred task counter. Read again after a stale write or uncertain receipt. Coordinate external editors; only Bots writers share its lock. A retained lock requires inspecting stopped owned work and the original host before manual recovery. Never remove a lock merely because the caller timed out.

## Assisted migration

Migrate only under an explicit user instruction to change task authority. Prepare and inspect the destination using the native source tools on the relevant host. Preserve the old source and record its old-to-new links in a retained mapping artifact. For Markdown, prepare `tasks.md` in the original home on its original machine and compute its hash there; a local file on a remote worker is not that destination. Quiesce relevant editors while confirming.

Use `tasks migration-confirm <bot-id> --revision <current-source-revision> --request-id <retained-uuid> --board <existing-id> --mapping '<JSON array of {from,to} references>' --evidence '<inspection/mapping reference>' --author <identity> --reason '<user instruction>'`. For a prepared Markdown destination, use `--markdown-hash <sha256>` instead of `--board`. The command validates the destination and atomically saves the source change and receipt. It does not verify the meaning of the supplied mapping or transfer content; confirm that work yourself before submitting. Keep larger mappings in a retained artifact referenced by the bounded receipt.

After uncertain delivery, inspect `tasks show` and `tasks migration-show <bot-id> <request-id>`. Identical replay recovers the original receipt and current authority without reverting a later choice; do not create a new request as a blind retry. Reconcile existing commitments explicitly with `commitment relink` after inspecting the mapping, including when returning to a previously used board or file. Links bind to that specific authority generation. Retain the migration-capable plugin build; older strict source readers can reject migration metadata. No source change authorizes deleting the old board/file, changing homes or restarting canceled work.

## Memory and in-turn capture

Use `memory remember <bot-id>` for enduring knowledge under the user's request or the bot's established memory policy. Supply a retained `--request-id`, `--topic`, complete `--markdown`, `--basis fact|inference`, original repeated `--source` identifiers, `--author` and `--reason`. Use thread/artifact/task/user source IDs without spaces, never sensitive forgotten text. Mark inference explicitly; one detailed-report request does not establish an enduring preference. Keep active obligations in commitments and temporary state in capture records. Use optional native BB memory in place; do not copy its facts or persistent IDs into Bots.

Retrieve bounded excerpts with `memory search`, then `memory show` only when relevant. Correct one record with complete fields and its current `--revision`; read again after a conflict or uncertain receipt. For derived notes, supply `--parents '<JSON [{id,revision}]>'`; known original sources are inherited and stale/excluded parents refuse. Summaries of one observation do not become independent evidence.

Use `memory forget <bot-id> <mem-id> --revision <current> --author <identity>` promptly for an explicit forgetting request. It suppresses the record, known sources and derived results from future retrieval. Historical content and live context may remain; report that limitation rather than claiming erasure or triggering an extra turn/clear. Unknown independent restatements cannot be reliably blocked. Do not recover forgotten text from old revisions or use a new source label to evade exclusion.

Before continuity or substantive handoff, capture recent state/decisions/summary in the current authorized turn. Read `capture progress <bot-id> --kind state|decision|summary --stream <source-id>`, inspect the original source window, then call `capture` with the ordinary content fields, matching kind/stream, retained UUID, `--revision <progress-revision>`, `--from <first-unprocessed>` and `--through <last-processed>`. Start at1 for revision0; thereafter continue from the previous boundary. The record and progress are atomic. Retain the UUID after uncertain delivery; identical replay never rewinds later progress. This captures evidence without sending a prompt, authorizing follow-up work or enabling idle maintenance.

## Checkpoints and export

Create a named checkpoint only under an explicit checkpoint instruction or approval: `checkpoint create <bot-id> --name '<label>' --request-id <retained-uuid> --author <identity> --reason '<instruction>'`. It pins display identity, SOUL, future execution defaults and eligible durable knowledge; it does not freeze tasks, commitments, capture progress, sessions or actions. After an uncertain receipt, reuse identical options to recover the same selection rather than creating another checkpoint.

Use `checkpoint list` / `show` for bounded metadata. Export with `checkpoint export <bot-id> <chk-id> --format json|markdown`, following `--after <nextCursor>` until null and retaining all pages. Current exclusions filter old selections; never recover omitted text from old revisions. Inspect user-authored content before sharing an export. A portable export is not a database backup or authority to replay work, alter a live session or replace a home. Import/purge remain unavailable.

Restore only under an explicit user instruction/approval for the selected records. Inspect the checkpoint and current target revisions, then call `checkpoint restore <bot-id> <chk-id> --selection '<JSON array of {kind,expectedRevision}, with id for knowledge>' --request-id <retained-uuid> --author <identity> --reason '<approval>'`. Kinds are profile, soul, execution and knowledge; select at most twenty. A stale revision, missing/excluded source or unavailable execution choice refuses the whole operation. Retain the UUID after uncertain delivery; identical replay reads its receipt without restoring again. Do not choose replacements for unavailable model references or evade exclusions. Restore appends revisions, keeps applied SOUL unknown and starts no native reconciliation, refresh, fallback or provider turn. Completed tasks/commitments, capture cursors, queues/actions and homes remain current.

## Commitments

When the user or current assignment creates an obligation, record it with `commitment add <bot-id> --what '<what is owed>' --author <identity> --reason '<instruction>'`. Add supporting references with repeated `--evidence`. The logical owner defaults to the calling owned conversation; use `--owner <logical-id>` only for a deliberate same-bot assignment. Retain `--request-id <uuid>` before scripted submission. After uncertain delivery, inspect that record; reuse the UUID only with identical content and attribution.

Use `--task <stable-task-id>` for a linked Tasks obligation, or `--markdown-reference '<literal-reference>'` in Markdown mode. Linked status belongs to that source. An unavailable, missing, wrong-board, changed-source or stale response is unknown status, not completion. Read Markdown status from the original host with `tasks read`; a stored literal reference does not verify a checkbox. Reconcile references with `commitment relink` using the current revision, author and reason after confirming the mapping. Do not close a linked shadow record or silently create a replacement task.

Use `commitment show` / `list` to inspect obligations; `list --after <nextCursor>` continues a page. Close an unlinked independent obligation with `commitment close <bot-id> <commitment-id> --revision <current> --author <identity> --reason '<completion evidence>'`. Read again after a revision conflict. These commands start no provider work and never update the external task source.

Automatic maintenance, continuity and fallback remain disabled. Create no workers or other background work during the initial setup acknowledgement. Do not invent memory commands before that feature ships.
