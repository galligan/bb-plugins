## Concrete queue compatibility result

The new durable kind is not readable by the pinned baseline. The [baseline payload mapper](https://github.com/get-bb/bb/blob/9816b9420d76b47c3cbff99fcc620c38527f0388/apps/server/src/services/threads/thread-queued-messages.ts#L158) only recognizes `inline` before taking the retry branch. A retained compact-first row has no retry request, attempt or reason, so this exact function throws `ApiError(500, "internal_error", "…is a retry with no original request")`. The [baseline public payload union](https://github.com/get-bb/bb/blob/9816b9420d76b47c3cbff99fcc620c38527f0388/packages/domain/src/queued-message.ts#L166) also rejects `{ "kind": "compact-first" }`.

The bounded check extracted the committed TypeScript functions and schemas by AST, transpiled them without changing their bodies, and supplied the real ApiError class and schema dependencies. Its input used the payload identity from the corrected runtime restart fixture, with null retry columns as written by the compact-first insertion path. The prototype reader returned `{ "kind": "compact-first" }`; the baseline reader threw status 500/code `internal_error`. Existing inline and retry controls returned identical payloads. Baseline kind/payload schema checks both returned false; prototype checks both returned true.

Evidence and reproduction script are attached to BOTS-18 as `19-queue-reader-compatibility.json` and `queue-reader-compatibility.mjs`, with copies under builder thread storage `bots-capabilities/`. The script resolves TypeScript/Zod from the isolated core checkout and uses Node 24 with `--conditions=source --import tsx`. It starts no server, writes no repository/database state and submits no provider request. This is a source-extracted reader check, **not** a full old-server startup, mixed-version client exercise or downgrade acceptance test.

Do not normalize retained rows to inline as an unreviewed workaround: that would discard the pending compaction requirement. Likewise, the absence of a SQL migration or daemon wire change does not make the public payload addition compatible with every older reader. The [chosen support boundary](support-boundary.md) no longer requires full backward compatibility: it gates the plugin through existing manifest fields and keeps post-upgrade data on the supported runtime. Older binaries gain no retroactive rejection; rollback requires the pre-upgrade snapshot procedure.
