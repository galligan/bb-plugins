# Minimum supported runtime and rollback boundary

Matt chose an explicit minimum supported BB/runtime and SDK version in the coordinating thread on 2026-11-10: “Ok well fine if we have a way to just have a minimum version supported somehow”. Full backward or in-place downgrade compatibility is not a v1 requirement if the restriction is enforceable and its consequences are documented. This supersedes requiring arbitrary old readers to understand the new compact-first payload. It does not waive upstream agreement, CI or the [remaining continuity matrix](continuity-matrix.md).

## Chosen mechanism

Use the existing public package manifest `engines.bb` and `engines.bbPluginSdk` together. Do not add a Bots compatibility service, a new core feature flag, or another queue. Once releases containing the accepted native admission contract are verified, set each engine range to `>=` its verified minimum. Pin the build-time `@get-bb/plugin-sdk` dependency separately to the version used to build and test the package.

| Value                         | Meaning and enforcement                                                                                                                                                                                                                                                            |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SDK dependency pin            | The declarations/build tooling used to produce Bots. Installing this npm dependency does not upgrade BB or its runtime SDK.                                                                                                                                                        |
| `engines.bb` minimum          | Checked against the BB app version supplied by the running server. Managed installs/updates reject an incompatible candidate; a path install can register but stays incompatible at load.                                                                                          |
| `engines.bbPluginSdk` minimum | Checked against the running host's `PLUGIN_SDK_VERSION`, independently of the plugin dependency. Managed installation rejects a too-new SDK requirement; path loading reports incompatibility before invoking the factory.                                                         |
| Development source pin        | A separate, isolated checkout of the reviewed core commit. App version `0.0.0` bypasses the app engine range; an unparseable app version also skips that load-time check with a warning. SDK checking still applies. Version strings alone do not verify a source build's content. |
| Persisted queue/data          | Written by core, independently of whether Bots is enabled. Neither engine field adds a database downgrade barrier or protects old clients from a new public payload kind.                                                                                                          |

The supported production distribution uses verified release builds with parseable nonzero app versions and both engine fields populated. Arbitrary development/custom binaries are outside that production boundary; isolated development requires the exact reviewed source pin and its separate capability results. A minimum version is a compatibility contract, not attestation against a binary that lies about its version.

There is **no selected numeric release floor yet**. A public registry check at 2026-11-11 00:24 UTC found latest SDK 0.6.138 and no published SDK 0.6.139; GitHub's latest BB release was desktop 0.49.0. The failing source baseline already used SDK 0.6.138. The prototype's proposed 0.6.139 string is not proof of an accepted/released contract and must not be copied into a release manifest as a supported floor. Evidence: `20-minimum-version-release-check.json`, attached to BOTS-18. These are dated observations, not an automatic version-selection rule.

Before any Bots release, verify that the chosen BB release and its actual runtime SDK contain the accepted change; run the acceptance matrix on that combination; then fill the real manifest fields and exact dependency pin. Verify a below-minimum app, below-minimum runtime SDK, the supported pair, and path-install activation behavior. Until that can be done, no production-supported Bots artifact is published or activated. There is currently no executable Bots package. BOTS-3/BOTS-18 remain incomplete and BOTS-4 remains behind BOTS-3.

## Existing enforcement evidence

The prototype core's [load path](https://github.com/galligan/bb/blob/05f2aa9b9c1e0a7eeb18c3f033860c8ae1b917cd/apps/server/src/services/plugins/plugin-runtime.ts#L1074) checks both engine ranges and [fails before the factory](https://github.com/galligan/bb/blob/05f2aa9b9c1e0a7eeb18c3f033860c8ae1b917cd/apps/server/src/services/plugins/plugin-runtime.ts#L1739). Its [update resolver](https://github.com/galligan/bb/blob/05f2aa9b9c1e0a7eeb18c3f033860c8ae1b917cd/apps/server/src/services/plugins/update-resolver.ts#L223) checks candidate app/SDK requirements and annotates the development exception. The [SDK compatibility helper](https://github.com/galligan/bb/blob/05f2aa9b9c1e0a7eeb18c3f033860c8ae1b917cd/apps/server/src/services/plugins/sdk-compat.ts) compares the requirement with the host constant. The older SDK 0.6.132 source snapshot `a124a8d4` also checks both fields before factory invocation; this is not a claim about every historical binary.

Ran five existing core suites with real SQLite and temporary plugin fixtures: SDK compatibility, manifest parsing, npm/Git candidate resolution, managed/path installation and plugin service loading. All **143 tests passed**. The suites demonstrate managed installation refusal and cleanup for a too-new app, refusal for a too-new runtime SDK, path-install incompatibility, load-time app incompatibility, compatible candidate selection and the development exception that still enforces SDK compatibility. Hypothetical test ranges such as `>=99.0.0` are test fixtures, not selected support floors. No user plugin was installed and no provider turn was started. Log: `minimum-version-tests.log`; source test names are recorded in `21-minimum-version-enforcement.json` on BOTS-18.

These tests verify the available mechanisms. They do not establish a released floor, live provider continuity, or a tested whole-system restoration procedure. Adding another plugin-side version check would not repair an older core reading persisted rows; reuse the existing gates instead.

## Upgrade and rollback procedure

The release boundary includes an operator procedure, because the baseline cannot retrospectively enforce a new restriction. Take a consistent, restorable **pre-upgrade snapshot before first startup of the changed core**, not merely before enabling Bots: native compact-before-send can write the new queue kind without Bots. Stop the relevant BB server/daemon processes and all writers while taking the snapshot. Preserve the complete BB data/plugin storage and matching binary/plugin versions, plus consistent copies of bot homes or other affected external files needed for recovery. Keep credentials in protected backup storage. Validate the backup and recovery process for the actual deployment before relying on it; this has not been exercised against production.

Upgrade to the verified supported runtime before enabling Bots. Let existing manifest checks refuse an unsupported plugin rather than start its factory. Existing core writes the new payload only in a core build containing that implementation; the release/version boundary does not add a retrospective write guard to old binaries.

**Do not open post-upgrade data with an unsupported older core.** Full in-place downgrade is unsupported. If rollback is necessary, stop the changed runtime and other writers, preserve its complete post-upgrade state for recovery, and restore the consistent pre-upgrade snapshot with its matching binary/plugin versions. Keep the post-upgrade copy separate and do not replay its queued rows into the old database. The restored state predates later conversations, checkpoints and other changes; preserve those separately for recovery with the newer supported runtime. This procedure is documentation, not authorization to replace production or restore a user's data automatically.

Disabling/uninstalling Bots, canceling visible queue entries, or observing zero compact-first rows does not certify that all post-upgrade data is downgrade-safe. Do not rewrite compact-first rows to inline, drop them, or dispatch canceled work to make an old binary accept the database. The new operation intent must not be silently lost.

The [observed baseline reader failure](continuity-matrix.md#concrete-queue-compatibility-result) remains a known limit: an old binary pointed at incompatible post-upgrade data can still emit its misleading 500. Plugin engine fields do not run before core database access and cannot change that old code. The actual protection is using the supported runtime for that data and restoring only the pre-upgrade snapshot for rollback. No retroactive rejection, automatic downgrade migration or old-client compatibility is claimed.

## Remaining release gates

Minimum-version-only support is now the chosen product boundary, so full backward/downgrade compatibility is no longer a blocker by itself. The remaining work is to get the upstream contract disposition, identify and verify actual releases/floors, pass CI and the live Stop/override/retry/clear/restart/coexistence and main/worker continuity matrix, and validate the deployment's backup/restore procedure. None of these permits installing the prototype into production. Existing Matt authorization for scoped investigation/implementation persists; no new product decision is required to use the manifest mechanism and this rollback policy.
