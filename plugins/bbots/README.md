# Bots

Persistent collaborators for BB, independent of the selected sidebar. The first default collaborator is Bob, with a main conversation named `@Bob`.

**Development preview:** `bb-plugin-bbots` (plugin ID `bbots`, display Bots) implements an additive create/open panel, persistent homes, revisioned identity/SOUL, future execution defaults, named native main conversations and explicit CLI-owned workers with reporting contracts. Automated continuity, maintenance and model fallback are not enabled. BOTS-6 creation and the original BOTS-17 create/open behavior passed bounded shared Dev checks; Matt subsequently reopened BOTS-17 for design alignment and missing settings. The correction below remains an offline preview awaiting its own reviewed runtime/visual acceptance; BOTS-8 workers and native reporting also passed the bounded Dev check below. Task-source/file features remain offline previews pending their own acceptance. Do not install it into a production instance as part of development.

The package uses the repository's published SDK pin, with BB >=0.49.0 / runtime SDK >=0.6.132 manifest minima. The build pin is not the installed runtime SDK. Preflight reports the installed stable BB separately; new behavior must be checked on the actual target. BOTS-3 tracks affected feature limits; BOTS-18 stays deferred/non-blocking. No custom production core is required.

## Create and recover

Open **Bots** in BB's existing navigation. Choose **New bot**, a connected machine and a name (Bob by default). Leave execution choices at BB defaults, or use the native model/reasoning/tier and permission pickers. A custom home base is optional and must be absolute; responsibility associations initially remain empty in this minimal UI and can be configured through the CLI at creation. The panel uses native ongoing conversations rather than embedding another chat or replacing a sidebar.

Hiding the browser page pauses bot-list and machine reads and disables creation and setup resume. Showing it again refreshes machine availability before those actions become available. Closing or navigating away lets BB unmount the page; browser visibility does not indicate whether every retained split pane is visible.

Select an existing bot to inspect setup and open its ongoing conversation. **Check / resume setup** can finish partial provisioning, including its initial acknowledgement; it never blindly replays an uncertain prompt. Offline/missing-home errors preserve the recorded home. The owned conversation's header identity action returns to its bot panel; ownership comes from SQLite, never its title or metadata. Thread drafts, Stop, queues, Info and normal controls stay with BB.

The browser retains a request key in tab session storage before sending creation. An uncertain response exposes a read-only request lookup, not another create attempt; remounting the form preserves that recovery path. Once its recorded bot is found, open that setup. Closing the browser tab can remove the local key, while SQLite intent and the bot list remain authoritative. No automatic write retry runs. If session storage is unavailable, the form refuses to send; use CLI creation with an explicit retained request ID instead.

Before a new request saves immutable intent, a read-only host call validates the base using that machine's native path rules, resolves existing ancestors and refuses repositories or protected data paths without creating directories. A known refusal returns to the retained form for correction; an unknown response keeps its recovery key. Existing requests continue to reconcile their recorded setup. Custom execution seeds the native picker from a usable provider catalog, skipping empty/failed catalogs within a total ten-second, sixteen-provider read budget; no model turn or automatic execution fallback is involved.

Use `bb bot create --machine <host-id>` for Bob, or add `--name Alice`. Creation is an explicit user-directed action that starts one short setup acknowledgement; it does not assign work. Use `--provider` / `--model` for an explicit native choice, or inherit BB defaults. `--request-id <uuid>` makes retries with identical options resolve the same bot. Scripts should retain this key before submitting; repeating a CLI invocation without it is a new creation request. Use `--json` for bounded structured output. If another plugin owns the alias, use `bb plugin run bbots ...`.

The default home is `~/.bb-bots/<stable-bot-id>` on the selected machine, outside BB's plugin data and repositories. `--home-base <absolute-directory>` chooses another base; the operator must keep it outside BB-managed disposable folders. Creation refuses Git repository locations, occupied paths without the matching marker and symlinked homes. It never overwrites, archives or deletes home artifacts. A rename changes the profile and managed main title, leaving the IDs, home and current pin preference intact.

`--association-mode none|all|selected` records responsibility independently of the main workspace; repeat `--project <id>` with `selected`. These choices do not load repository instructions, adopt other threads or grant permissions. The native home project is a container for the main conversation, not a replacement for associations.

Use `bb bot list`, `show <bot-id>`, `resume <bot-id>` and `rename <bot-id> --name <name> --revision <current-revision>`. `list` returns at most 100 rows and a `hasMore` indicator. Resume verifies the recorded machine/home and existing main, and reconciles partial creation. It never resends the initial prompt, respawns an uncertain main or repins an existing thread. Offline or missing established homes produce visible errors; restore the original home/marker before resuming. Do not point an existing bot at a new empty directory as recovery.

Creation records SQLite intent before native side effects. The first ordinary dispatch binds exclusive main ownership from that intent before session construction; metadata is only a lookup mirror, not ownership authority. A lost receipt after this point recovers the recorded thread. If project creation lost its receipt or main creation failed before ownership was durably bound, the outcome is visibly uncertain and automatic adoption/recreation is disabled. Pre-existing home project matches are refused rather than adopted. Inspect the original native request and the bot's home project/queue; do not rerun with a new request ID as a blind retry. A successful Stop does not certify cancellation of held queue entries; use native queue cancellation to discard unwanted pending work. Bots cannot veto native Send now or another plugin's compaction/retry operations.

A small revisioned starter SOUL is created and supplied at configuration resolution so the first session has standing guidance. Soul text is not a live home file; session guidance is bounded to 16,000 characters. No idle/failed listener, schedule or automatic wake is registered.

Run package `bun run check`, `bun run test` and `bun run build`, then the repository verification before pushing. The real `server.ts` and `host.ts` are loaded through public SDK harnesses; provider timing, native Stop/queues, real routing and retirement require the separately scheduled Dev slot.

## Soul and execution defaults

Use `bb bot soul show <bot-id>` and `soul update <bot-id> --revision <current> --markdown <complete-markdown> --author <truthful-identity> --reason <user-instruction-or-approval>`. Updates preserve Markdown verbatim, append an attributable revision and reject stale bases, blank text or more than 16,000 characters. The `bbots-soul` skill helps propose a deliberate persona edit; ordinary observations and maintenance do not authorize rewriting it.

The display distinguishes current revision, last supplied revision and applied revision. **Applied revision is unknown:** the public synchronous configure callback can run without constructing a new provider session and has no session receipt. A newer edit is pending supply; a matching last supplied revision is still unverified for the live session. Editing starts no turn and performs no clear, compact or refresh. This limitation remains BOTS-3/BOTS-11 work rather than a fabricated applied marker.

Use `models show <bot-id>` / `models update <bot-id> --revision <current-or-zero> --defaults '<complete-json>' --author <identity> --reason <instruction>` for revisioned future conversation choices. JSON has `main`, `worker` and `fallback` fields. Each choice accepts native `providerId`, `model` and `reasoningLevel`; main/worker also accept `permissionMode` (`accept-edits`, `auto` or `full`). Start with `{"main":{},"worker":null,"fallback":null}`: omitted native choices inherit BB policy, and a null worker inherits the whole main choice. An explicit worker object is independent. Provider/model/reasoning availability is checked by BB when constructing the conversation, not asserted by saving this document. Fallback cannot change permissions and automatic fallback remains disabled.

Saving defaults does not mutate an existing main. Use its native BB controls for current execution choices; the minimal UI uses native pickers for new bot creation. New main creation accepts `--reasoning` and `--permissions` alongside provider/model, and pending pre-spawn setup uses the latest saved main defaults. `bb bot brief <bot-id>` pulls bounded current identity, home, revision/defaults and the calling owned worker's current contract. It does not inject full SOUL or assume fresh memory/task state. The UI's selected native service tier is preserved through creation rather than discarded.

## Owned workers and native reports

`bb bot work '<assignment>' --title '<short task>' --project <project-id> --environment <ready-environment-id> --author <identity> --reason '<instruction>'` starts one explicitly assigned normal native conversation named `→ @<bot> <task>`. An owned caller supplies its bot; other callers select `--bot <bot-id>`. The first slice reuses an existing ready, active environment in the selected project and its connected machine. It does not move the main home or create another environment provider. Main-home unavailability does not force a worker on another machine to move or stop. Native construction checks provider/model availability and permissions; the worker inherits the revisioned effective worker choice without enabling fallback.

Retain `--request-id <uuid>` before scripted submission. SQLite atomically records the logical worker, immutable request and first attributable contract before native creation. First ordinary dispatch verifies the selected project/environment/machine and binds exclusive ownership before configuration, including an ordinary human follow-up to a pending plugin-created thread. Metadata is only a lookup mirror. `work list <bot-id>` returns up to 100 bounded summaries and `hasMore`; `work show <conversation-id>` returns its setup and current agreement. `managedTitlePending` exposes a bot rename that raced worker creation; resume reconciles that title without replaying work. Replaying identical options returns the recorded attempt rather than respawning it. Unknown pre-admission outcomes remain visibly uncertain, including after reload; inspect native history and queue before choosing another action. No second message broker or automatic retry is involved.

Workers are independent unless `--parent <thread-id>` selects a native parent in the working project. Parent notifications default off; `--parent-notifications auto` may duplicate explicit reports. Report destinations are separate: `--report-thread <id>` selects an ordinary physical thread; `--report-conversation <id>` selects a stable owned logical conversation. Omission records the bot's main as the initial target. `--report-when`, `--stop-when`, `--context` and repeated `--source` populate the human-readable agreement; report content defaults to result, evidence, uncertainty and next action. Workers evaluate triggers themselves. No completion listener, subscription engine or idle wake runs.

Use `contract show <conversation-id>` / `contract update <conversation-id> --revision <current> --agreement '<complete-json>' --author <identity> --reason '<instruction>'`. The JSON fields are `assignment`, `context`, `sources`, `reportWhen`, `reportTo`, `reportContent` and `stopWhen`. A destination is `{"kind":"conversation","conversationId":"…"}` or `{"kind":"thread","threadId":"…"}`. Deliberate reassignment appends a revision and checks its target; it starts no turn and does not reparent or resume work. Explicit bot rename reconciles managed main and worker titles while preserving identity, environment and pin preference; ordinary resume does not fight manual titles. A pass updates at most 100 worker titles; a visible pending result asks for another resume if more remain. Missing/moved native worker records must be reconciled before their managed rename can finish.

`msg '<message>'` resolves an owned caller's current main; that caller cannot override its owner with another `--bot`. An unowned caller must select `--bot` explicitly. `report '<message>'` requires the caller's SQL-owned contract and never substitutes a main. `reply '<message>' --seq <native-incoming-sequence>` uses that message's native agent sender, not a name or thread ID inferred from prose. Owned logical destinations resolve their current verified mapping at send time; unbound, missing, archived and self targets are refused without reopening them. Native caller context supplies sender attribution; it is routing context in a full-trust plugin API, not a new authentication boundary. An explicit bot selector does not adopt a caller or establish report authorship.

All three use native queue-if-active delivery, retaining sender attribution and returning acceptance plus queued-row/wait evidence where available. An idle recipient can start a new turn, including after native Stop; the framed message and operating skill explicitly prohibit treating it as permission to resume a canceled assignment. Model adherence is not a universal veto over provider behavior. Acceptance does not prove reading, completion or a response, and an uncertain transport result does not trigger a resend. The bounded worker/Stop/reply check below is actual runtime evidence; it does not certify other providers, automatic cutover or arbitrary model behavior. Automatic successor cutover remains disabled, so no unverified predecessor-routing guarantee is claimed.

## Markdown task source preview

When Tasks is absent at the initial task-source choice, use `bb bot tasks markdown-init <bot-id> --revision 0 --author <identity> --reason '<instruction>'`. Bots checks installed-plugin inventory; disabled Tasks or an unknown inventory is not absence. It journals the original home host/path and a unique initialization intent before asking that host to create `tasks.md`. An occupied file is preserved. If file creation/write/sync fails partway, a partial file can remain; inspect it on the original host before manual repair. Resume refuses mismatched content even when the initialization intent is known. After an uncertain response, inspect `tasks show`, then explicitly run `tasks markdown-resume <bot-id> --revision <shown-revision> --author <identity> --reason '<confirmation>'`. That operation verifies the exact initial file/intent, never adopts another file or switches authority.

`tasks read <bot-id>` returns bounded UTF-8 Markdown and its SHA-256. Use `tasks write <bot-id> --hash <current-hash> --markdown '<complete-file>'` to replace the file verbatim. Both route to the recorded home host even for workers on another machine; an owned caller cannot read or write another bot's complete task file. Writes use an exclusive host lock, reject stale hashes and replace through a same-directory temporary file. They preserve conflicting, symlinked, multiply-linked or oversized files rather than overwriting them. A failed or uncertain receipt requires a fresh read before another edit; there is no automatic write retry. Bots serializes its own writes. Coordinate external editors separately; an external writer does not participate in that lock.

An interrupted `.bbots-tasks.lock` is a visible recovery conflict; Bots will not steal or delete it automatically. Confirm that owned work is stopped and inspect the original home before manually recovering a stale lock. Reading an established missing file/home never recreates it. Later Tasks installation or a home-host outage preserves the chosen Markdown authority and starts no migration. No arbitrary Markdown task counts are inferred.

The bot detail uses BB's native file link with an explicit host target for `tasks.md`, or native Tasks navigation for a configured tracker. Availability/recovery failures remain visible. The compact brief includes source metadata and availability, without injecting the entire Markdown file. This source and UI slice has offline actual server, host and app entry evidence; live host/UI acceptance remains separately scheduled. These source commands do not transfer content or change an established authority; use the explicit confirmation below after preparing a migration.

## Commitments

`bb bot commitment add <bot-id> --what '<obligation>' --author <identity> --reason '<instruction>'` records a stable obligation and its logical conversation owner. The owner defaults to the calling owned conversation, or the selected bot's main for an unowned operator; `--owner <logical-id>` must belong to that bot. Retain `--request-id <uuid>` before scripted creation. Replaying identical content and attribution returns the same current record, including after closure/reload; changed options refuse. Revisions retain what is owed, owner and up to 20 evidence references supplied with repeated `--evidence`.

An unlinked obligation owns `open` / `closed` status. Close it with `commitment close <bot-id> <commitment-id> --revision <current> --author <identity> --reason '<evidence>'`. Link to the configured source with `--task <stable-task-id>` or `--markdown-reference '<literal-reference>'`. A linked Tasks status is read from public Tasks `getTask` at each request, with board/ID validation and a five-second bound; it is never persisted as a second status. Outages, deletion, wrong-board responses and authority changes return unknown status with a visible reason. A late response after a reference/source revision changes is discarded without a retry.

Markdown references identify the original home-host file and literal location. Their status is explicitly unknown to Bots: read the authoritative file through `tasks read`; arbitrary Markdown is not parsed into authoritative statuses. Linked obligations cannot be independently closed. Reconcile a changed reference with `commitment relink` using the expected revision and attribution; source history and original commitment revisions remain intact. Owned callers cannot read or edit another bot's commitments through these commands; native CLI context remains full-trust routing context, not an authentication boundary.

`commitment show` returns one record; `commitment list` returns at most 20 and a stable `nextCursor` accepted by `--after`. `brief` includes up to ten commitments with clipped obligation text, their status availability and a continuation cursor, alongside the current worker contract and task source. It omits evidence bodies and the full Markdown file. These are explicit read/write commands with no worker, provider turn, external task mutation, background refresh or automatic migration. Their real server-entry tests are offline evidence; task/file acceptance is separately scheduled.

## Assisted task-source migration

Migration is user-directed and agent-assisted. Prepare and inspect the destination using the native Tasks/file tools under that instruction; preserve the original board or file. For Markdown, prepare `tasks.md` in the bot's original home on its original machine and compute its SHA-256 there. Bots does not copy, convert, create or delete destination content. Record old-to-new links and a reference to the inspected full mapping before changing authority.

Confirm with `bb bot tasks migration-confirm <bot-id> --revision <current-source-revision> --request-id <retained-uuid> --board <existing-tracker-id> --mapping '[{"from":"OLD-1","to":"NEW-1"}]' --evidence '<inspection or full mapping artifact reference>' --author <identity> --reason '<user instruction>'`. Replace `--board` with `--markdown-hash <sha256>` for the prepared original-home file. The mapping has 1–20 reference pairs, each reference at most 512 characters; larger mappings belong in a retained artifact linked from those references/evidence. This is an operator attestation, not automatic semantic/content verification. Quiesce the relevant editors during confirmation: the hash/board observation and SQLite commit do not lock an external application or filesystem across machines.

Bots checks the destination board exists, or reads the prepared file on the original home host and compares its hash. It then atomically appends an attributable migration receipt plus the new task-source revision. Stale revisions, unavailable/missing destinations, changed file hashes and cancellation before the commit leave the old authority intact. The receipt records original and destination pointers, supplied mapping/evidence and request options. `tasks migration-show <bot-id> <request-id>` retrieves it; `tasks show` includes the latest `migrationId`. Exact replay returns that receipt and the current authority even after a later migration; it never reverts the later choice. Changed request options refuse.

Existing linked commitments preserve their original references and unknown status after an authority change. Reconcile each deliberately with `commitment relink` after inspecting the mapping; no status or link is copied automatically. Initial Markdown absence rules still apply to initial setup; explicit migration is a separate user-authorized operation. No provider turn or background worker is started. Source, file and migration acceptance still needs a scheduled runtime packet; these commands have offline real server/host-entry evidence only.

Migration receipts use existing revisioned SQLite documents, without a core or table migration. Confirmed sources and links created or explicitly reconciled under them carry a `migrationId` understood by this implementation. Returning to an earlier board or file does not reactivate an unreconciled link. Earlier strict source/commitment readers can reject this metadata. Keep a migration-capable plugin build after confirmation. A source-path downgrade alone is not a rollback: use a separately authorized consistent pre-change backup with matching plugin code and preserved homes/external sources if restoration is necessary. No downgrade/restore or live migration was performed by this implementation.

## Memory and ordinary-turn capture preview

`bb bot memory remember <bot-id>` records durable knowledge with a retained `--request-id <uuid>`, `--topic`, complete `--markdown`, explicit `--basis fact|inference`, original repeated `--source` identifiers, `--author` and `--reason`. Source identifiers use `thread:`, `artifact:`, `task:` or `user:` prefixes with no spaces; use identifiers, not sensitive text or mirrored shared-memory facts. `--parents '<JSON [{id,revision}]>'` links current same-bot records and inherits their known original provenance; an inferred parent cannot silently become fact.

Use `memory search` for bounded topic/text excerpts and stable `--after <nextCursor>` pagination; `--kind` separates knowledge from state/decision/summary captures. `memory show <bot-id> <mem-id>` reads one current record. `memory correct` supplies the complete replacement fields and `--revision <current>`, appending history rather than overwriting another thread's change. Exact creation replay recovers the current record, including after correction or forgetting, without duplicating it.

`memory forget <bot-id> <mem-id> --revision <current> --author <identity>` suppresses that record, its known source IDs and provenance-derived knowledge/captures from later reads and briefs. Capture windows and canonical native message origins are indexed automatically. Forgetting a window suppresses overlapping captures and derivatives; later disjoint input can still be captured. Whole-stream exclusions cover the entire stream. Operational exclusions remain outside selected checkpoint revisions. Historical revisions, conversations and previous exports can retain content; live provider context is not cleared. The same fact independently restated under an unknown source cannot be reliably recognized. Import/purge and verified session refresh remain later capabilities, not promises made by forgetting.

For substantive progress inside an already authorized turn, read `capture progress <bot-id> --kind state|decision|summary --stream <source-id>`. Then `capture <bot-id>` uses the same content/attribution fields plus `--kind`, `--stream`, `--from <first-unprocessed-sequence>`, `--through <last-processed-sequence>`, `--revision <progress-revision>` and retained `--request-id`. Use a whole native thread as its stream and cite individual messages as sources. Initial progress is revision0/through0; start at1 and continue contiguously. If another kind has already forgotten the next input, a later `--from` can cross only a gap wholly covered by retained exclusions. The same transaction records `excludedBefore` in the cursor revision without storing forgotten content; an uncovered sequence or stale revision still refuses the write. The captured record and processed boundary commit atomically. Replaying after later progress recovers current progress without rewinding or skipping uncommitted input. The agent attests the inspected source window; Bots does not scan or semantically verify its transcript. State snapshots do not replace authoritative Tasks/commitment status.

All these commands send nothing and perform no model-backed maintenance. Briefs pull a small current knowledge/capture index; they do not inject full records into every new session. BB shared memory remains optional and is used through its own tools in place, with no Bots mirror or persistent cross-store references. The implementation adds only operational provenance/exclusion tables to the existing revisioned document store; new runtime/restore/export acceptance is separately gated. Automatic continuity/dreaming stay disabled.

## Checkpoint/export source preview

Use `bb bot checkpoint create <bot-id> --name '<label>' --request-id <retained-uuid> --author <identity> --reason '<explicit instruction>'` to save a named immutable selection. It atomically pins display identity, SOUL, resolved future execution defaults and eligible durable knowledge revisions. Reusing identical options recovers the original checkpoint after later edits; changed request options refuse. `checkpoint list <bot-id>` returns up to ten headers, with `--after <nextCursor>` for the next page. `checkpoint show <bot-id> <chk-id>` returns metadata and selected-document count.

`checkpoint export <bot-id> <chk-id> --format json|markdown` emits one selected document plus profile/default metadata. Continue with `--after <nextCursor>` until `nextCursor` is null; retain all pages for a complete export. JSON has `format: bbots-checkpoint` and `schemaVersion: 1`; Markdown wraps the same portable data. IDs, revisions, original provenance and attribution remain inspectable. Current forgetting exclusions apply on every page, including for an old checkpoint. Its original selection count can therefore exceed the exported document count. A previous export cannot be recalled by forgetting.

This selection excludes homes/project associations, task authority, commitments, recent capture records/cursors, native conversation/routing/session state, pending actions, credentials, installation settings and transient downloads. Allowlisting structured fields does not detect secrets a person wrote into SOUL, names, notes or attribution; inspect the explicit export before sharing it. No files are written, provider turns started or native state restored. Selective restore is an offline preview described below; import/purge and runtime/continuity acceptance remain separate work. Schema12→14 appends two tables; keep a checkpoint-capable build after adoption rather than automatically downgrading.

`checkpoint restore <bot-id> <chk-id> --selection '[{"kind":"soul","expectedRevision":3},{"kind":"knowledge","id":"mem_<uuid>","expectedRevision":2}]' --request-id <retained-uuid> --author <identity> --reason '<explicit user instruction/approval>'` deliberately restores up to twenty selected records. Choose `profile`, `soul`, `execution` or `knowledge`; knowledge requires its stable ID. Read each target's current revision first (`models show` for execution). Revision zero means no execution document exists. The whole operation appends revisions atomically, preserving intervening history and records added after the checkpoint. A stale selection, excluded source or failed receipt write changes none of the selected records.

Retain the restore UUID. Identical replay returns its content-free receipt and never repeats writes, including after later edits or forgetting. Changed options refuse. Historical same-bot provenance parents can be retained during this explicit restore, while ordinary corrections still require current parents. Exclusions remain monotonic, are rechecked after any asynchronous lookup and cannot be rolled back. SOUL's applied revision remains unknown; existing sessions and native titles are not refreshed. A restored profile name can leave managed titles pending until a later explicit supported reconciliation.

An execution selection validates saved provider/model/reasoning/service/permission choices using the original host's current public catalog under a ten-second lookup bound. Missing/offline/unknown choices refuse without substitution. Empty/inherited native choices remain omitted; this is a current host observation, not a guarantee of later or other-workspace availability. No permissions are changed on a live thread, no fallback runs and no provider turn starts. Selecting only other records does not require catalog access. Restore never resets task authority/status, commitments, capture cursors, native routing/sessions, queued messages or actions. No home/project association is moved or restored.

A portable export is not a full instance backup. For a consistent physical backup, an operator must separately use the owning public SQLite connection's `backup()` and verify integrity, preserving compatible code, database and homes. Copying only a live `data.db` can omit WAL state. No automatic database backup/restore or rollback is implemented here.

## Continuation preparation preview

`bb bot continuity prepare <bot-id> --conversation <logical-id> --request-id <retained-uuid> --author <identity> --reason '<authorized-turn evidence>'` saves a checkpoint and bounded continuation references for the selected owned main or worker. It records current SOUL, task-source and reporting-contract revisions, up to ten obligation references, three knowledge references and one state/decision/summary reference each. Recent captures are selected by that physical thread's canonical `thread:<thread-id>` source, so another worker's newer capture cannot replace its state. No note bodies or queued-message text are copied into the preparation.

The checkpoint and preparation commit atomically. Exact replay returns the original preparation without another native observation or checkpoint; changed options refuse. A changed logical mapping, cancellation, archived/missing native source or failed write leaves no partial checkpoint. Preparation starts no Compact, clear, refresh, send, retry, pickup or successor, and never authorizes side-effect replay.

`continuity show <bot-id> <cnt-id>` filters newly excluded knowledge/capture references and reads current task authority, commitment statuses and reporting contract. A selected revision that has since changed is labeled with both revisions. Completed work stays completed; current unavailable authority stays unknown. New obligations can push a saved reference off the current ten-record status page: it then reports null current status with `not-in-status-page`. Read that specific `commitment show`, or continue `commitment list` with `currentCommitmentsNextCursor`; absence from this page is not completion. Stored observations are explicitly historical: use `continuity readiness <bot-id> --conversation <logical-id>` for a fresh bounded native observation. Native status is separate from queue evidence. Output keeps at most twenty queue IDs and a twenty-event lifecycle window, with truncation/inconsistency visible; the public queue API itself returns the thread's queue without pagination. No queue content is returned, moved or canceled.

Readiness grants no dispatch authority and always reports transitions disabled in this slice. Usage needs a nonestimated timestamped snapshot at most sixty seconds old; missing/estimated/future/old measurements, a newer clear/compaction or an equally recent/newer usage event from a different session are not fresh. An older previous-session event cannot invalidate a newer snapshot. A bounded window without a manual Stop does not prove consent, and idle does not prove process settlement or provider-session pickup. The native reads share a ten-second bound. Current declarations at both SDK0.6.132 and the repository pin expose these read contracts; that does not prove the native compaction admission/caller-attribution contract changed. Automatic compaction, clear/re-brief, fallback and verified successor cutover remain separate BOTS-11/BOTS-3 gates. This reference preparation is a foundation for that goal, not a claim that seamless continuity has shipped.

## Storage behavior

Profile creation atomically records its first audit revision and an unbound logical main ID. Name changes preserve those IDs. Document writes (including SOUL.md) use expected per-record revisions; revision zero creates a new document. Stale edits fail instead of overwriting another writer. Revision history records author, reason and time; callers must supply truthful attribution. Markdown is retained verbatim, bounded to 65,536 characters per revision. No live file synchronization or automatic persona rewriting is performed.

Initial physical-thread binding is idempotent and exclusive. It cannot replace an already bound thread; a future verified continuity operation must own that transition. No ownership is inferred from thread titles or metadata. Creation validates public inputs and native thread ownership against persisted intent. Checkpoint/export/selective restore is an offline BOTS-16 preview. Factory/storage initialization alone creates no homes or native conversations.

The focused suite uses real SQLite, independent connections for stale-write tests, rollback fault injection, SDK reload and a separate Node process reopening committed records. Tests pin better-sqlite3 13.0.3 for its packaged prebuilds under the repository's `--ignore-scripts` install policy; production continues to use the public host-owned database handle.
